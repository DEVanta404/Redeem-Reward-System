# Supabase Admin and RLS Migration

Review [SUPABASE_ADMIN_SECURITY_MIGRATION.sql](SUPABASE_ADMIN_SECURITY_MIGRATION.sql) and run it manually in the Supabase SQL Editor. The Flutter app does not execute migrations. Do not rerun the older `SUPABASE_SCHEMA.sql` as an RLS update; it contains permissive client point and daily-reward policies.

The migration does not delete existing rows. It assigns the admin role by matching `auth.users.id`, adds/updates deal pricing, creates `order_items` price snapshots, and replaces RLS policies for the tables used by the app. It also creates default user profiles on Auth sign-up without reading a role from user metadata and adds `deals` and `orders` to Supabase Realtime when the publication exists. Sales totals are computed in admin-only Postgres RPCs; reward claims use the existing `transactions` redemption rows.

Orders created before order-item price snapshots existed cannot have their historical price recovered. The migration preserves their existing order JSON and backfills an unknown unit price as `0.00` rather than substituting today's price.

## Important Before Applying

The base migration includes a `redeem_reward(p_reward_id)` RPC and protects direct client point updates. The current Flutter build uses that RPC for reward redemption. Cart checkout calls `place_order(p_items)`, which reads the current server-side deal price and inserts its snapshots. The `get_sales_summary`, `get_deal_sales`, and `get_reward_claims` RPCs explicitly reject non-admin callers.

The migration is not applied automatically. Back up the project database and review the SQL before running it. Never put a Supabase service-role key in the Flutter app.

## Password policy and in-app notifications

After reviewing and applying `SUPABASE_ADMIN_SECURITY_MIGRATION.sql`, review and run `SUPABASE_PASSWORD_NOTIFICATIONS_MIGRATION.sql` in the Supabase SQL Editor. The newer migration adds the `must_change_password` profile flag and private notifications with RLS, then updates the existing order, redemption, and order-status RPCs. Apply it before deploying the corresponding Flutter build. Notifications are generated by the database in the same transaction as each operation; existing orders are not backfilled.

The Flutter redemption path now calls `redeem_reward(p_reward_id)`. Do not apply the migration while using an older app build: its previous direct profile-point update is not compatible with the protected redemption policy.

### Supabase Auth password settings

In the Supabase Dashboard, open **Authentication → Sign In / Providers → Email** (in some dashboard layouts this is **Authentication → Settings → Password Security**):

- Set **Minimum password length** to `8` (12 is the app's recommended length).
- Enable required uppercase, lowercase, numeric, and symbol characters.
- Enable **Leaked password protection** / Have I Been Pwned checks if it is available on your project plan.
- Save the changes and test registration and password change through the deployed Auth flow.

The app-side validator is additional protection, not a substitute for these Auth settings. Supabase Auth does not provide server-side checks for user-name or email-name fragments, so those rules are validated in Flutter.

Reset any known weak test accounts before enabling the new Auth password rules. Supabase may reject sign-in for existing passwords that no longer meet the project's configured requirements; see [Supabase password security](https://supabase.com/docs/guides/auth/password-security).

### Resetting weak test-account passwords

Passwords are stored as hashes; the app cannot inspect or audit existing passwords. To reset test accounts:

1. Open **Authentication → Users**, select a test account, and use the dashboard's password recovery/reset action to send a recovery link. Complete the reset with a password that meets the policy.
2. For accounts without an accessible email, run a one-off Supabase Admin API script locally using the project's `service_role` key in a local environment variable. Call `auth.admin.updateUserById(userId, { password: newPassword })`; do not put the key in Flutter, source control, or logs, and remove the local secret after the reset.
3. For a forced in-app change, open **Table Editor → public.profiles**, find the account, set `must_change_password` to `true`, and save. The app blocks user and admin accounts at login until their Auth password is successfully changed. The database trigger clears the flag when Auth changes the password hash.

Never query password hashes to assess password strength. Reset or flag accounts based on your own test-account list.
